## Context

当前 `/agent` 页面已经具备历史回放的底层能力：页面会从 URL 读取 `threadId`，`AGUIChat` 会在收到 `threadId` 后调用 `GET /ai/api/v1/conversations/messages` 回放该线程历史消息。因此，“按已知 `threadId` 打开历史”这条链路已经存在，只是缺少用户可见入口。

现状中的关键缺口有两个：

- APO 前端没有左侧历史列表，用户无法在页面内发现自己的历史线程。
- 外部 AgentSRE 会话历史服务虽然已经有 `conversations.user_id` 字段，但当前列表查询不是按用户过滤，创建写入链路也仍把 `user_id` 固定写成伪用户，无法支撑“按 creator 查看自己的历史”。

此外，`AGUIContext` 中现有的本地 session 管理是一个被关闭的简化实现，依赖 localStorage，并且在载入旧 session 时会重新生成新的 `threadId`。这套模型与本次要接入的服务端 conversation history 不是同一套语义，因此不能作为本期历史列表的实现基础。

约束如下：

- 页面入口仍然是现有 `/agent`，不新增独立历史页面。
- 左侧列表只显示当前登录账号自己创建的线程。
- 基于 `threadId` 的 URL 直达本期继续保留，用于兼容轻量分享。
- 不做历史标题回填，不要求一期强制接入摘要标题。
- 本期不暴露历史删除或重命名 UI，也不依赖现有删除接口的权限语义。
- 桌面端默认使用固定双栏；窄屏设备允许退化为可展开历史面板，但不能损失历史查看、打开和续聊能力。
- 当前商业仓前端改动主要位于 `frontend/src/pro/**`；历史会话后端能力依赖外部 AgentSRE 仓配合。
- `/agent` 页面前端属于商业仓独有路径，本次默认不涉及 OSS `feat/agent-ce`。

## Goals / Non-Goals

**Goals:**

- 在 `/agent` 页面内提供固定可见的历史对话列表。
- 让左侧列表严格按 creator / 当前账号维度展示历史线程。
- 保持点击历史线程、URL 刷新、手工输入 URL、分享直达都能回到同一线程。
- 让用户从自己的历史列表打开历史线程后仍能继续追问，并沿用原始 `threadId`。
- 让线程切换或返回新对话时同时隔离 run 与线程级诊断状态，避免旧线程 findings / evidence / detail 残留。
- 给出稳定的一期标题和时间展示规则，并与排序语义保持一致。

**Non-Goals:**

- 不实现管理员查看所有用户历史。
- 不在本期加入搜索、筛选、删除、重命名、收藏、置顶、标签等列表增强能力。
- 不做历史存量线程的标题补齐或批量摘要。
- 不在本期把 `threadId` 直达替换成显式 share token / share link。
- 不重做 AGUI 的本地 session 管理功能。

## Decisions

### Decision 1: 在现有 `/agent` 页面内做双栏布局；窄屏允许退化为历史面板

`/agent` 将保持单页入口，桌面端新增左侧固定历史列表，右侧继续复用现有聊天主区域。窄屏设备如果无法稳定承载固定双栏，允许退化为可展开历史面板。无论采用哪种布局，列表点击行为都只更新选中线程和 URL，不做页面跳转。

这样可以直接复用现有 `AGUIProvider`、消息回放和续聊能力，也让刷新与直达行为天然收敛到同一条 `/agent?threadId=...` 语义上。

Alternatives considered:

- 单独新增“历史会话页”：信息架构更重，且会把查看历史与继续追问拆成两步。
- 将历史入口放进弹窗或下拉：实现更轻，但可发现性差，不符合“长期可见入口”的目标。
- 在所有屏宽上强制固定双栏：实现统一，但在窄屏上会明显挤压聊天主区域。

### Decision 2: 历史列表与 URL 直达采用两套并存的访问语义

本期显式区分“可见列表范围”和“已知线程访问能力”：

- 左侧历史列表只返回当前登录账号作为 creator 的线程。
- `GET /messages?threadId=...` 继续允许通过已知 `threadId` 直达打开线程，即使当前用户不是 creator。
- 通过 URL 打开的外部线程不会自动写回当前用户的左侧历史列表。

这让“我的历史”与“一期轻量分享”可以同时成立，也为后续把 `threadId` 直达收敛为显式分享能力预留了边界。未来若引入 share token，只需要替换“详情访问是否允许”这条规则，不需要重做左侧列表的 creator 语义。至于非 creator 是否还能在共享线程上继续写入，本期不把它定义为 APO 侧正式 contract，但本次也不要求为此额外增加主动拦截。

Alternatives considered:

- 一期直接禁止跨 creator 的 `threadId` 打开：安全边界更紧，但与已确认的分享需求冲突。
- 一期同时引入 share token：边界更清晰，但范围明显扩大，不适合作为这次基础可用性改动。

### Decision 3: 会话 creator 采用现有 `Conversation.user_id`，并在创建时绑定真实当前用户

不新增数据库列，直接将现有 `conversations.user_id` 作为 creator / owner 字段。实现上需要修正外部 AgentSRE 的会话创建链路，使其写入真实当前登录账号，而不是固定伪用户。

creator 是线程级归属，不因后续是谁通过分享链接打开、继续追问而被重写。换句话说，线程归属是“谁创建的”，不是“最后谁访问的”。

Alternatives considered:

- 新增单独的 `creator_id` 字段：语义更显式，但当前已有字段足够，属于无必要扩表。
- 用“最后活跃用户”覆盖 creator：会破坏“我的历史”列表的稳定归属，也不利于后续分享能力演进。

### Decision 4: 历史列表接口返回最小稳定契约，时间展示与排序共用 `timeValue`

一期历史列表返回最小字段集：

- `threadId`
- `title`
- `timeValue`

其中 `timeValue` 是排序与展示共用的原始时间字段。理想语义是最近活跃时间；若一期无法稳定提供最近活跃时间，则允许整个版本统一使用创建时间。前端只负责基于 `timeValue` 进行格式化显示，不自行推断另一套排序字段。

如果一期使用最近活跃时间，那么该字段语义定义为“线程级最近持久化活动时间”，不区分本次产生该活动的是 creator 还是通过分享直达打开该线程的其他用户。这样的线程级活跃变化 MAY 刷新 creator 视角下的列表排序，但 MUST NOT 改变 creator 归属，也 MUST NOT 让访问者因此获得左侧列表归属。

时间展示规则固定为：

- 1 小时内：`N 分钟前`
- 当天且超过 1 小时：`N 小时前`
- 昨天：`昨天 HH:mm`
- 7 天内：`N 天前`
- 超过 7 天：`YYYY-MM-DD HH:mm`

Alternatives considered:

- 前端同时拿多个时间字段自行选择：灵活，但容易产生排序和显示不一致。
- 后端直接返回最终格式化字符串：前端控制力差，也不利于国际化和后续规则调整。

### Decision 5: 历史标题一期固定为首条用户提问，不做回填

新线程首次建立时，标题直接持久化为首条用户提问。旧数据如果已有标题则直接使用；缺失标题的旧数据展示确定性占位文案，不阻塞列表展示。不做历史批量回填，也不把摘要标题作为一期上线前置条件。

这样可以在不引入额外异步摘要链路的前提下，快速给出可读标题，并把未来“摘要标题 + 首问回退”能力留作独立演进项。

Alternatives considered:

- 一期强制上摘要标题：体验更好，但依赖更重，且失败回退策略需要额外定义。
- 完全不持久化标题、列表只显示占位符：实现最轻，但可用性过低。

### Decision 6: `threadId` 是当前选中历史线程的唯一来源，不复用本地 session 模型

前端选中状态以 URL 中的 `threadId` 为源头：

- 点击左侧列表项时更新 URL。
- 页面首屏或刷新时从 URL 读取 `threadId` 并加载历史。
- 清空当前对话时移除 `threadId`，回到新对话状态。
- 在从自己的历史列表打开的历史线程上继续发送消息时，继续沿用当前 `threadId`。

实现上不启用现有 `ENABLE_SESSION_MANAGEMENT` 本地会话逻辑，因为该逻辑依赖 localStorage，且加载历史时会生成新 `threadId`，与服务端 conversation thread 的语义相冲突。

Alternatives considered:

- 恢复本地 session 管理并做兼容：会混入两套会话模型，复杂度高且容易出现 threadId 漂移。
- 让右侧聊天状态独立于 URL：会削弱刷新和分享直达能力。

### Decision 7: 采用“后端先保证归属与列表契约，前端再接历史列表”的落地顺序

虽然当前前端已经能按 `threadId` 回放，但如果后端仍然把 creator 写成固定伪用户，或者列表接口仍返回全部会话，则左侧“我的历史”会立刻失真。因此落地顺序必须是：

1. 先修正外部 AgentSRE 的 creator 写入语义。
2. 再让列表接口按当前账号过滤并返回稳定字段。
3. 最后在 APO `/agent` 页面接入历史列表与 URL 同步。

Alternatives considered:

- 先做前端列表、后端晚些修：能更快看到 UI，但数据错误会直接暴露给用户。

### Decision 8: 新对话从首条用户消息开始就必须形成可直达线程

当用户处于“新对话”状态并发送第一条用户消息时，前端必须为该线程建立 `threadId`，并在首条消息发出时或不晚于发出后立即将该 `threadId` 写入 URL。这样无论用户是在回答过程中刷新，还是在回答完成后刷新，都能回到同一线程。

该线程在后端持久化成功后，必须出现在当前用户的左侧历史列表中，不要求整页刷新。实现可以选择局部刷新列表、增量插入当前线程，或在发送成功后重新拉取当前列表页，但都必须保证标题和归属语义与后端一致。

Alternatives considered:

- 只在用户显式点击某条历史记录时才写 URL：会导致新线程在首次提问后仍不可刷新恢复。
- 只有整页刷新后才让新线程出现在历史列表：可行但交互割裂，且不利于用户理解“当前线程已被保存”。

### Decision 9: 切换线程或回到新对话前，必须先隔离流式回答并重置线程级诊断状态

当前 `AGUIContext` 通过事件订阅持续接收 run 结果。如果用户在回答尚未结束时点击另一条历史记录、或清空当前对话回到新线程状态，而系统没有先停止或隔离当前 run，那么旧 run 的后续事件就可能被渲染到错误的线程视图中。与此同时，前端当前还持有 findings / evidence / detail 等线程级诊断状态与缓存；如果切换线程时只更新消息列表，而不清理、重建或重新按 `threadId` 分区这些状态，就会把上一个线程的诊断信息残留到当前线程。

因此本期要求：当用户准备切换到另一条历史线程或回到新对话状态时，如果当前 run 仍在进行，前端必须先取消、解绑或显式隔离该 run，并在进入目标线程前清理、重建或重新分区 findings / evidence / detail 等线程级状态与缓存。具体交互可以是自动取消，或先提示用户确认后再取消，但最终效果必须同时保证跨线程消息不串流，且不会展示旧线程残留的诊断信息。

Alternatives considered:

- 允许用户直接切换，依赖后端自然结束旧 run：风险最高，最容易产生消息串线程。
- 在运行中完全禁用历史列表：实现简单，但会明显削弱历史入口的可用性。
- 仅取消 run、不处理线程级诊断状态：会留下 findings / evidence / detail 残留，无法满足线程隔离要求。

### Decision 10: 一期不暴露历史删除或重命名操作，也不依赖删除权限语义

本次能力目标是“查看并打开自己的历史”，而不是“治理历史”。虽然外部服务已存在删除接口，但当前需求没有定义删除入口、分享线程删除后的语义，也没有把删除权限模型纳入本期范围。因此 APO 侧本期不新增删除或重命名入口，也不把现有删除接口的权限语义作为能力边界的一部分。

这样可以避免把列表可见性、详情直达与删除权限耦合在一期中一并处理，也让后续若要补“删除自己的历史”或“分享线程删除后谁可见”时，能够单独设计。

Alternatives considered:

- 直接暴露现有删除接口：实现看似更快，但会把权限、分享链路和误删恢复语义一起带进范围。
- 前端不暴露入口但隐式依赖删除权限语义定义可见范围：边界含混，容易让“我的历史”与“可直达线程”产生规则冲突。

### Decision 11: APO 将 creator 维度 `/conversations/list` 视为唯一受支持契约

当前 owner 仓部分文档仍可能把 `/conversations/list` 描述成“返回全部会话列表”。但对 APO `/agent` 历史列表能力而言，受支持契约必须明确收敛为“返回当前登录用户作为 creator 的历史线程”。实现阶段需要同时确认 APO 当前仓没有其他受支持页面依赖旧的“全部会话”语义。

这样可以把当前能力的依赖边界说明白，避免 APO 一边按 creator 维度实现“我的历史”，另一边又默认列表接口仍承担全量会话浏览职责。

Alternatives considered:

- 在 APO 内同时兼容 creator 语义与全量语义：短期灵活，但契约含混，容易让不同页面消费出不同理解。
- 等 owner 仓所有文档和消费者都完成迁移后再推进 `/agent`：依赖链过长，会阻塞本次核心体验改进。

### Decision 12: 历史列表能力要求“最终可达全部历史”，但首屏加载必须有界

产品能力上，用户必须能够访问自己账号下的全部历史对话；但实现层不应在 `/agent` 首屏对当前用户历史做无界全量拉取。历史列表可以采用分页、游标或“加载更多”形式做增量加载，只要最终能够遍历到全部历史，并且排序、选中和时间展示语义在跨页时保持一致。

这条约束主要用于避免把当前 AgentSRE `/conversations/list` 的无界 `.all()` 语义直接搬到 `/agent` 首屏交互上。

Alternatives considered:

- 首屏一次性拉取全部历史：实现最直接，但在历史量增大后会直接拖慢 `/agent` 首屏。
- 只展示最近若干条，不提供继续加载：会违背“能看到全部自己的历史对话”的产品目标。

### Decision 13: 历史侧栏默认收起，header 常驻开关；顶部不显示运行状态条；侧栏样式必须跟随明暗主题

为了避免 `/agent` 首屏默认被左侧栏挤压，同时保留历史入口，一期桌面端与窄屏都统一使用可收起的历史栏，且默认收起。桌面端继续使用 `antd Layout.Sider`，窄屏继续使用 `Drawer` 退化形态，但顶部 header 必须常驻历史开关，确保用户在任意状态下都能重新展开历史栏。

同时，本次不再在聊天主区域顶部显示运行状态条。运行中、断链或线程加载失败等状态不再通过顶部 strip 占位展示，聊天区域保持更干净的主视图。对于不存在或已删除的 `threadId`，前端应改为右上角短暂提示可恢复错误，而不是在聊天主区域持续占位显示 404 类错误。

视觉上，历史栏及其列表项不能继续依赖浅色硬编码背景，而必须收口到当前主题 token，保证亮色与暗色主题下都具备可读的边界、hover 和 active 对比。

Alternatives considered:

- 桌面端默认展开：入口更直接，但会长期挤压聊天区，不符合本次收口目标。
- 用单独的侧栏 rail trigger 替代 header 开关：也可行，但当前结构里 header 常驻开关改动更小。
- 保留顶部状态条只隐藏运行中态：会继续占据顶部空间，也不符合“顶部状态条不要”的明确要求。

## Repo Scope / Ownership

**本仓库（APO commercial repo）负责：**

- `/agent` 页面布局、左侧历史列表 UI、点击与选中交互、时间格式化、空状态与错误态展示
- `threadId` 与 URL 同步、首条消息后的新线程 URL 写回、运行中切线程保护
- 线程切换或返回新对话时的 findings / evidence / detail 状态隔离
- 前端 API 适配、类型定义和 `pro` 侧 i18n 文案
- creator 维度 `/conversations/list` 契约在当前仓的消费收口，以及对当前仓其他受支持页面的兼容性核对

对应路径：

- `frontend/src/pro/views/agent/**`
- `frontend/src/pro/components/AGUIChat/**`
- `frontend/src/pro/api/conversation.ts`
- `frontend/public/locales/*/pro/**`

说明：

- 这些都是商业仓独有路径，本次默认不涉及 OSS `feat/agent-ce`。
- 本期不在当前仓新增历史删除或重命名入口。

**AgentSRE 仓负责：**

- 会话 creator / owner 的真实用户绑定
- 历史列表按 creator 过滤
- `threadId/title/timeValue` 列表契约
- 历史回放接口的无效 `threadId` 错误语义
- 列表分页或增量加载契约（如果由后端承载）

对应路径：

- `api/controllers/chat.py`
- `api/controllers/conversation.py`
- `api/models/conversation.py`
- 必要的 schema / identity helper

**其他仓或基础设施仅在以下条件下进入范围：**

- 如果当前 APO -> AgentSRE 的调用链没有稳定传递真实当前用户身份，那么拥有该透传链路的网关、代理或认证集成层仓库需要补充最小改动。

这类改动是“条件依赖范围”，不是本次需求默认主范围；只有在 apply 阶段确认现有链路无法满足真实用户绑定时才展开。

## Risks / Trade-offs

- [保留 `threadId` 直达意味着一期不会收紧跨账号访问边界] → 明确把它视为轻量分享行为，并在设计上把“列表可见范围”和“详情直达权限”拆开，为后续显式分享收口预留接口。
- [共享线程下，creator 是线程级字段，不能表达每条消息是谁发的] → 一期接受该限制，不把参与者 / 访问者审计纳入范围；后续如果分享能力升级，再单独扩展参与者模型。
- [如果后端一期只能返回创建时间，列表“最近活跃”体验会弱一些] → 允许一期统一退回创建时间，但必须保证排序和展示都使用同一字段，避免认知冲突。
- [如果一期使用线程级最近活跃时间，分享访问可能刷新 creator 列表排序] → 在文档中显式接受这一语义；如果实现阶段认为体验不可接受，则退回创建时间作为 `timeValue`。
- [旧数据缺少标题时会出现占位文案] → 使用确定性兜底，确保列表完整可见；后续再以独立需求处理历史标题治理。
- [APO 前端依赖外部 AgentSRE 仓配合] → 将跨仓接口契约固定在 `threadId/title/timeValue` 和 creator 语义上，前后端联调按该最小契约推进。
- [小屏幕直接常驻双栏可能挤压现有聊天区] → 实现阶段必须验证窄屏布局，必要时在窄屏上退化为可展开历史面板，但不能破坏与桌面端一致的历史能力。
- [owner 仓将 `/conversations/list` 从“全部会话”收敛为 creator 语义可能影响旧消费者] → APO 侧把 creator 维度视为唯一受支持契约，并在实施阶段核对当前仓其他受支持页面是否依赖旧语义。

## Migration Plan

1. 确认 APO -> AgentSRE 现有调用链是否已经能透传真实当前用户；本 change 最终采用 `userId` 作为唯一 request identity 参数，REST 路径通过 query 传递，`POST /srechat` 通过 body `forwardedProps.userId` 传递。
2. 在外部 AgentSRE 会话创建链路中，将 `Conversation.user_id` 绑定为真实当前登录账号，并保持 creator 不可被后续访问者覆盖。
3. 调整历史列表查询接口，仅返回当前登录账号创建的会话，并输出 `threadId`、`title`、`timeValue`；若首屏不做全量拉取，则同时定义分页或增量加载契约。
4. 在 APO 当前仓内核对 `GET /conversations/list` 的现有消费者，确认没有其他受支持页面依赖旧的“全部会话”语义。
5. 保持 `GET /conversations/messages?threadId=...` 的线程回放能力不变，并确保无效 `threadId` 返回可恢复错误。
6. 在 APO `/agent` 页面引入左侧历史列表 UI，并实现桌面固定列表、窄屏可展开历史面板、新线程首发后的 URL 写回，以及列表增量刷新或局部刷新。
7. 在前端补充运行中切线程保护、findings / evidence / detail 状态隔离、空状态、异常态和时间格式化逻辑，确认用户从自己的历史列表打开线程后继续追问仍沿用同一 `threadId`，且本期不暴露删除/重命名入口。
8. 端到端验证 creator 列表隔离、URL 直达分享、刷新恢复、新线程首发、增量加载、自己的历史线程续聊、标题兜底、时间展示规则、线程级状态隔离与窄屏行为。

Rollback strategy:

- 如果前端上线后需要快速回退，可以先移除左侧历史列表 UI，而保留已有 `threadId` URL 回放能力。
- 如果后端 creator 绑定或列表过滤出现问题，可回退对应 AgentSRE 变更；本期不要求新增表结构，因此不存在数据库迁移回滚成本。

## Open Questions

- 外部 AgentSRE 一期能否稳定提供“最近活跃时间”；如果不能，则直接按创建时间作为 `timeValue` 上线。
- 缺失标题时的占位文案最终使用哪一条 i18n 文案，可在前端实现阶段定稿，但不影响本次能力边界。
