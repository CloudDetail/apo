# 健康度待处理事项异常分析迁移智能体设计

日期：2026-09-09
状态：方案定稿，前端实现已完成并通过定向测试与生产构建

## 1. 目标与范围

将健康度页面中的异常分析从“前端调用专用后端 AI 接口并在当前页面展开结果”，统一调整为：

1. 用户点击“异常分析”或服务详情中的指标分析入口。
2. 前端把当前异常上下文组装成一条面向智能体的问题。
3. 跳转到 `/agent`。
4. 智能体使用自身可访问的指标、日志、Trace、告警、实例和资源工具进行验证并回答。

范围包括两处入口：

- 健康度总览页“待处理事项”列表中的“异常分析”。
- 服务详情页“服务健康助手”弹窗中红色或黄色指标的分析入口。

两处入口使用同一套问题构造逻辑，区别只保留在路由来源标记，便于后续统计和定位。

## 2. 当前实现与真实触发链路

### 2.1 页面入口

- 页面路由：`/healthy-service`
- 页面组件：`frontend/src/pro/views/systemHealthOverview/index.jsx`
- 待处理事项组件：`frontend/src/pro/views/systemHealthOverview/components/PendingIssueQueue.jsx`

待处理事项由服务指标状态构造。后端 `buildSystemHealthPendingIssues` 会把服务指标状态为 `red` 或 `yellow` 的项加入候选列表：

- `red`：异常
- `yellow`：关注
- `green`、`gray`：不会进入待处理事项列表

前端加载列表时请求 `/api/system-health/pending-issues`，当前页面请求使用 `status: 'abnormal'`，后端会将其归一化为 `red`。因此当前这个列表实际展示的是红色异常；黄色虽然会被后端候选构建逻辑生成，但不会被这条列表请求返回。黄色主要会在服务详情中的“服务健康助手”链路中出现。

### 2.2 点击后的现有行为

当前按钮回调链路为：

```text
PendingIssueQueue “异常分析”
  -> SystemHealthOverviewPage.analyzeIssue(issue, analysisKey)
  -> POST /api/system-health/pending-issues/analyze
  -> 当前页面保存 issueAnalyses
  -> 成功后在列表下方展开 PendingIssueAnalysis
```

当前请求携带字段：

```json
{
  "groupId": 1,
  "serviceName": "service-gateway-springboot",
  "metricKey": "errorRate",
  "relativeTime": "15m"
}
```

当页面使用绝对时间窗口时，时间字段改为：

```json
{
  "groupId": 1,
  "serviceName": "service-gateway-springboot",
  "metricKey": "errorRate",
  "startTime": 1750000000000000,
  "endTime": 1750000900000000
}
```

### 2.3 后端收到请求后的行为

接口入口：

- `backend/pkg/router/router_api.go`
- `backend/pkg/api/systemhealth/func_analyzependingissue.go`

后端不会直接相信前端列表中的指标值，而是根据 `groupId` 和时间窗口重新构建系统详情，然后用 `serviceName + metricKey` 查找问题。

后端的实际步骤：

1. 根据 `groupId` 和时间窗口重新查询系统详情。
2. 在当前系统详情中查找指定服务和指标。
3. 如果该指标已经恢复，或者不再是 `red` / `yellow`，返回 `pending issue not found or recovered`，不会继续请求 AI。
4. 组装 `SystemHealthPendingIssue`。
5. 按时间窗口和问题内容计算缓存键；命中缓存时直接返回缓存结果。
6. 检查 AI 是否启用、Base URL、模型和 Wire API 配置。
7. 调用 Responses 或 Chat Completions 兼容接口。
8. 将 AI 结果清洗成固定字段并返回前端。

当前后端传给 AI 的问题数据包括：

```json
{
  "groupId": 1,
  "systemName": "stuck-demo",
  "serviceName": "service-gateway-springboot",
  "metricKey": "errorRate",
  "metricLabel": "错误率",
  "status": "red",
  "value": "79.34%",
  "note": "当前请求错误率",
  "serviceScore": 20,
  "systemScore": 35
}
```

### 2.4 当前后端 AI 的分析约束和输出

当前后端 Prompt 的分析边界是：

- 只能根据服务、指标状态、当前值和指标说明生成内容。
- 不得编造日志、Trace、告警、变更记录、根因或其他未提供上下文。
- 证据不足时，必须在 `dataBoundary` 中说明数据边界。
- 固定输出三个步骤：`定位`、`排查`、`处置`。

返回字段包括：

```json
{
  "aiStatus": "succeeded",
  "issue": {},
  "analysis": "事件说明",
  "impact": "影响说明",
  "actionPlan": [
    { "phase": "定位", "target": "...", "action": "...", "validation": "...", "risk": "..." },
    { "phase": "排查", "target": "...", "action": "...", "validation": "...", "risk": "..." },
    { "phase": "处置", "target": "...", "action": "...", "validation": "...", "risk": "..." }
  ],
  "validation": "恢复验证",
  "risk": "风险",
  "dataBoundary": "数据边界"
}
```

## 3. 当前触发条件总结

### 待处理事项列表

当前“待处理事项”列表中，只有以下条件同时满足时，用户才看得到“异常分析”按钮：

1. 健康度时间窗口已经解析成功。
2. 用户有权访问的系统中存在待处理服务指标。
3. 该服务指标在当前列表过滤结果中为 `red`。
4. 待处理事项接口成功返回该条数据。

点击后，当前专用 AI 请求还要求该问题仍满足后端的红黄状态校验：

1. 后端按 `groupId + 时间窗口` 重新查询成功。
2. 指定 `serviceName + metricKey` 仍然存在。
3. 指标仍为 `red` 或 `yellow`；对当前列表按钮来说通常是 `red`。
4. 后端 AI 配置完整且 Wire API 受支持。

页面加载、健康度刷新、时间范围切换本身不会自动触发该 AI 分析；必须用户点击按钮。

### 服务健康助手弹窗的现状

服务详情中的“服务健康助手”在打开弹窗或切换指标页签时，会自动调用同一个 `/api/system-health/pending-issues/analyze`。这条链路的触发条件是服务或服务指标中存在 `red` / `yellow`。

迁移后，打开弹窗和切换页签只负责展示异常指标摘要，不再自动请求模型；用户点击当前指标的“在 Agent 中分析”后，才跳转智能体并自动发送问题。

## 4. 定稿的迁移方案

### 4.1 触发链路

待处理事项按钮采用以下链路：

```text
健康度总览 PendingIssueQueue “异常分析”
  -> buildPendingIssueAgentPrompt(issue, queryParams)
  -> navigate('/agent', { state: { agentLaunch } })
  -> Hermes Agent 创建新会话
  -> 填充问题并自动发送一次
  -> 智能体查询证据并回答
```

服务详情链路相同，只是来源标记为 `system_health_service_issue`：

```text
服务健康助手指标页签 “在 Agent 中分析”
  -> buildPendingIssueAgentPrompt(issue, queryParams)
  -> navigate('/agent', { state: { agentLaunch } })
  -> Hermes Agent 创建新会话
  -> 填充问题并自动发送一次
  -> 智能体查询证据并回答
```

建议新增独立的 `agentLaunch` 状态，不复用当前 `workflowLaunch`，原因是：

- `workflowLaunch` 表示从任务库选择了明确的 Workflow。
- 它携带 `workflowId`、版本和 Workflow 名称。
- 健康度异常分析是普通智能体问题，不应伪造或绑定一个 Workflow。
- 复用会导致发送时错误地附带 Workflow ID，改变 Hermes 运行路径。

推荐的路由状态形状：

```ts
interface AgentLaunchContext {
  goal: string
  source: 'system_health_pending_issue'
  autoSend: true
}
```

调用示意：

```ts
navigate('/agent', {
  state: {
    agentLaunch: {
      goal: buildPendingIssueAgentPrompt(issue, queryParams),
      source: 'system_health_pending_issue',
      autoSend: true,
    },
  },
})
```

### 4.2 智能体页面行为

建议点击后自动发送，而不是只把问题放入输入框等待二次点击。原因是用户对“异常分析”的预期是立即获得分析结果。

智能体页面需要处理以下状态：

1. 接收到 `agentLaunch` 后创建新对话，避免把异常分析追加到用户正在进行的历史会话。
2. 将 `goal` 填入输入框状态。
3. 等待用户身份、Hermes session client 和会话创建条件就绪。
4. 自动发送一次，不附带 `workflowId`。
5. 发送成功后把当前会话 ID 写入 URL，保持历史会话可定位。
6. 立即清理 `location.state`，避免刷新页面重复发送。
7. 使用一次性发送键或 ref 防止 React effect 重渲染导致重复提交。
8. 发送失败时保留问题文本，让用户可以手动重试；不能静默丢失问题。

### 4.3 健康度页面行为

待处理事项列表按钮和服务详情指标入口点击后都不再：

- 调用 `/api/system-health/pending-issues/analyze`。
- 在当前健康度页面展示模型返回的分析卡片、加载动画或展开/收起结果。

待处理事项页面仍然继续使用待处理事项接口展示当前列表，也继续支持打开系统健康度详情。服务详情弹窗仍保留指标页签、当前值和状态摘要，但分析结果统一在 Agent 页面展示。

## 5. 智能体问题设计

### 5.1 必须携带的异常上下文

问题至少应包含：

| 字段 | 用途 |
| --- | --- |
| 系统名称 | 确定异常所属系统 |
| 数据组 ID | 智能体查询工具支持时用于限定数据范围 |
| 服务名称 | 查询指标、日志、Trace 和实例 |
| 指标名称与 metricKey | 明确异常类型，避免只传中文展示名 |
| 当前状态 | 区分异常 `red` 和关注 `yellow` |
| 当前值 | 提供触发时的观测值 |
| 指标说明 | 帮助理解指标语义和异常含义 |
| 分析时间窗口 | 保证智能体查询与异常判断使用同一窗口 |
| 系统列表和数据组 ID | 同一服务/指标跨多个系统聚合时限定查询范围 |

不携带服务健康分、系统健康分等页面汇总字段。这些字段是页面展示和排序依据，不能直接帮助 Agent 定位根因。

### 5.2 推荐问题模板

```text
请分析以下服务指标异常，并通过当前可访问的可观测数据验证原因。

【异常查询上下文】
系统范围：订单系统，数据组 ID：1001
服务：order-api
异常指标：错误率（errorRate）
异常等级：异常（red）
当前观测值：5.70%
指标含义：错误率超过异常阈值
分析时间窗口：最近 15 分钟

【分析要求】
1. 判断该异常的实际影响范围，以及是否影响请求成功率、响应时延、可用性或其他用户体验。
2. 围绕上述异常和时间窗口，查询有助于排查故障的数据，只选择有助于验证结论的证据。
3. 给出有证据支撑的根因候选，区分已确认事实、推断结论和仍需验证的假设。
4. 输出定位、排查、处置和恢复验证建议，明确下一步应执行的查询或操作。
5. 不要只复述上述异常摘要；不要编造不存在的日志、Trace、告警、变更记录或根因。如果某类数据不可访问，请明确说明数据边界。
```

### 5.3 聚合行的特殊处理

待处理事项表格会按 `serviceName + metricKey` 聚合多条系统问题。一个表格行可能同时代表多个系统，但当前旧后端分析请求只携带一个主 `groupId`，后端也只重新解析该主系统。

迁移到智能体时建议把聚合行的全部系统名称和可用 `groupId` 都放进问题中，例如：

```text
系统范围：订单系统，数据组 ID：1001；支付系统，数据组 ID：1002
```

同时要明确：页面聚合数据只能说明异常范围，不能直接证明这些系统的根因相同。智能体应按系统分别查询或明确无法区分的原因。

## 6. 后端接口的处理建议

### 当前阶段保留

保留 `/api/system-health/pending-issues/analyze`，但当前健康度前端不再调用，理由：

- 可能存在旧版本前端或其他调用方。
- 后端接口、缓存和相关测试可以作为兼容入口保留，降低发布期间的兼容风险。
- 当前页面的两条入口已经统一迁移到 Agent，不再形成旧接口与 Agent 两套用户体验。

### 后续再评估

当确认仓库内外没有旧客户端或其他调用方后，再考虑删除接口及其缓存、Prompt 和响应模型。删除前需要完成：

1. 仓库内调用检索。
2. 前端灰度或版本兼容确认。
3. 运行时访问日志确认无旧客户端调用。
4. 后端接口下线说明和回滚方案。

## 7. 失败和边界行为

### 智能体不可用

推荐保留已生成的问题文本，并显示在输入框中，允许用户手动发送或修改；不要退回到待处理事项页面内静默生成另一套旧 AI 结果，否则会造成两种分析入口语义不一致。

### 异常已经恢复

迁移后，点击发生在列表展示时，问题文本使用页面当时的快照。智能体实际查询时可能发现指标已经恢复，应在回答中明确“触发时异常、当前已恢复”，不能把历史触发状态当成当前仍异常。

### 时间窗口缺失

健康度页面当前设计要求先解析时间窗口再加载数据。问题构造时仍应携带解析后的 `relativeTime` 或 `startTime/endTime`；若异常情况下没有窗口，应明确写成“当前健康度查询时间窗口”，并由智能体先确认可用查询范围。

### 数据不可访问

智能体应区分：

- 页面已经确认的事实。
- 通过工具查询得到的事实。
- 根据事实做出的推断。
- 因工具、权限或数据缺失暂时无法确认的内容。

不允许因为页面只有一个指标值，就直接输出确定根因。

## 8. 验证计划

本次实现已补充并执行以下验证：

### 单元测试

- Prompt 包含系统、服务、metricKey、状态、当前值、说明、分数和时间窗口。
- `red` / `yellow` 状态文本正确。
- 聚合多个系统时不会丢失系统列表和数据组 ID。
- 绝对时间窗口和相对时间窗口均可生成可读文本。
- 空字段有稳定兜底，不生成 `undefined`。

### 前端行为测试

- 待处理事项按钮调用 `navigate('/agent')`，不再调用专用分析 API。
- 路由状态使用 `agentLaunch`，不复用 `workflowLaunch`。
- 智能体收到问题后只自动发送一次。
- 刷新智能体页面不会因为历史 `location.state` 重复发送。
- 自动发送失败时问题仍保留在输入框。
- 服务健康助手弹窗只展示异常摘要，点击指标入口后跳转 Agent，不再自动请求旧分析接口。

### 手工验收

1. 点击一条 `red` 异常，确认跳转智能体并自动产生一条用户问题。
2. 确认智能体回答中实际查询了可观测数据，而不是只复述页面字段。
3. 点击一条 `yellow` 异常，确认问题中状态和处理目标正确。
4. 制造同服务同指标跨多个系统的聚合行，确认问题携带完整系统范围。
5. 在指标恢复后再让智能体查询，确认回答能说明当前状态与页面触发状态的差异。
6. 打开服务详情中的服务健康助手，分别点击红色和黄色指标的“在 Agent 中分析”，确认均跳转并自动发送。

## 9. 已确认决策

本次实现采用以下决策：

| 决策项 | 推荐方案 | 原因 |
| --- | --- | --- |
| 点击后是否自动发送 | 是 | 用户点击的是“异常分析”，预期是直接获得回答 |
| 是否复用 `workflowLaunch` | 否 | 健康度问题不是 Workflow 运行 |
| 是否保留旧后端接口 | 是，当前阶段保留 | 兼容旧版本前端和其他潜在调用方 |
| 是否迁移服务助手弹窗 | 是 | 两处入口都改由 Agent 统一分析，避免保留两套模型行为 |
| 是否把 `groupId` 放进自然语言问题 | 是 | 便于智能体工具限定查询范围；工具不支持时仍可作为上下文 |
| 是否将聚合行拆成多个智能体问题 | 否，先发送一个带完整范围的问题 | 保持一次点击一次分析；由智能体决定是否逐系统查询 |

## 10. 结论

当前“异常分析”本质是一个同步的、后端专用 AI 报告生成动作：页面传入 `groupId`、服务、指标和时间窗口，后端重新确认指标仍为红/黄后，基于有限健康度字段调用 AI，并在页面内展示固定格式报告。服务详情弹窗打开或切换指标时还会自动触发这条链路。

迁移后的职责改为：健康度页面只负责提供可靠、完整、带时间窗口的异常上下文；智能体负责继续查询证据、关联多类可观测数据、形成根因候选和行动建议。待处理事项和服务详情两处入口都通过独立的 `agentLaunch` 路由状态连接，并采用一次性自动发送机制。原页面内 AI 分析结果、加载动画和展开/收起样式不再保留。
